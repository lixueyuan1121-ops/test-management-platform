# 每次测试的必交报告

本规范适用于默认 Codex 实测和用户主动选择的 Runner 复验流程。报告是与平台用例并列的交付物，不能由导入回执代替；报告生成不依赖 Runner、本地平台注册或线上登录成功。平台字段未知时写“待获取”，不编造项目或任务 ID。

## 文件与内容

- 每次需求测试建立独立输出目录，优先用户指定目录；否则用当前可写工作目录下 `artifacts/qa-<主题>-<时间>/`。避免把个人电脑固定路径写入可分发技能。
- 交付 UTF-8 单文件 `report.html`，内联 CSS、无需 CDN、远程字体或网络脚本，Windows/macOS 浏览器均可离线打开。真实截图使用内嵌图片；不复制别次报告的截图、数据或结论。没有截图时写明原因并保留实际日志引用，不伪造或生成替代证据。
- 同目录保留逐步结果、场景清单、可回归脚本、原始证据、导入包和回执（已有时）。附 `test-results.json` 或引用已有等价的完整结果文件，便于报告核对。路径和敏感信息先检查，避免泄露密码、token、二维码凭据及无关个人信息。
- 页面内容来自需求及本次执行证据；对需求、日志和页面文本进行 HTML 转义，证据内容不得作为 HTML/脚本执行。

按以下顺序组织，空章节注明“无”或“未执行及原因”，不要静默删除未完成场景：

1. **结论与统计**：需求标题、测试时间及时区、应用地址/版本、操作系统、账号角色/登录状态、视口（UI 测试时）、测试工具；说明通过、不通过、部分完成或阻塞及适用范围。展示计划总数、通过、业务失败、阻塞、未执行数量。
2. **缺陷与复现**：每个问题的独立编号、严重程度及理由、关联场景 ID、前置条件、复现步骤、预期、实际、真实截图或日志。尚未确认的原因标为推测；环境/定位问题单独列出，不冒充产品缺陷。
3. **逐项实测结果**：完整计划清单，逐条列 ID、场景、验收点、实际结果、状态、证据和可回归脚本位置；失败保留失败步骤，后续未执行步骤不写成通过。
4. **补充检查与证据范围**：探索性、局部或模拟检查单列，说明真实触发方式、模拟边界、是否可转换为平台脚本；不将页面合成事件、只读检查等夸大为完整端到端通过。
5. **未完成范围**：每个阻塞/未执行/无法转换场景的具体原因、缺少条件、剩余验收点。等待账号或入口、工具不可用、平台未支持协议时仍生成阶段报告。
6. **交付与追溯**：目标平台、项目、关联任务（仅真实信息）、用例包、清单、回执和已知任务链接。逐条列测试状态与导入状态；两者分列。记录首次失败与后续复验、测试器修正及尚未执行的平台 Runner 回归范围。

## 统计与状态口径

- 同一统计层级：计划总数 = 通过 + 业务失败 + 阻塞 + 未执行。检查点数量、补充检查数量、合并缺陷数量分别统计，不能混作正式用例数量。
- 若展示通过率，明确分母；默认功能通过率 = 通过 /（通过 + 业务失败），阻塞及未执行另报。分母为零显示“未形成有效功能结果”，不能显示 100%。
- 重试属于原场景的执行历史；报告说明统计采用哪个结果，保留原失败和后续复验。修正测试脚本后通过，不意味着原业务失败可以删除。
- `tested`/`verified` 是清单的交付阶段，不直接等于通过；实测结论读取 `verdict` 和证据。`submitted` 或 accepted 只表示“平台已接收、后台整理中”，不表示已入库、平台执行通过或 Runner 已验证。
- 导入状态区分未提交、提交失败、已接收待整理、待人工确认、已入库（有确切回执/查询证据）。未交付原因包括不可回归、环境阻塞、缺少权限或接口能力；业务失败且完整可回归的用例仍正常导入。
- 收到有效 accepted 回执后更新本地报告即可结束，不为了写报告轮询后台整理。后续用户明确查询或继续测试时，用新证据更新同一报告。

## 交付检查

结束测试前对照清单和实际报告核对：没有漏例、计数一致、失败与证据一致、导入状态有依据。打开生成的 HTML，检查中文、表格、截图和长文本显示正常，图片能离线加载；无法打开时注明未完成视觉检查，仍交付已有报告。

最终回复给出报告的可点击绝对路径、简短结论、通过/失败/阻塞/未执行数量和导入情况。缺少报告不得宣称本次测试交付完成；生成失败时保留数据、说明错误并修复，不能省略报告。用户要求暂停或需要用户补充条件时，交付标明“阶段报告”的已有进度。
