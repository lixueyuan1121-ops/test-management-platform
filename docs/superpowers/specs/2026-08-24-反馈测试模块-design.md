# 反馈测试模块 设计文档

**状态:** 已评审(对话逐节确认)｜**日期:** 2026-08-24

## Goal

机器人把用户反馈加工成「需求 + 用例」的 md(可能多文件打包 zip)推给平台;平台新增
与「功能测试」「对话测评」同级的**「反馈测试」**模块,把导入内容重新拆解成结构化、
可自动化执行的用例 → 组成回归用例集 → 支持**定时自动回归 / 手动整集回归 / 勾选用例即时执行**
三种触发,最终复用已验证的 qalab-runner 通道执行回写、按批次展示结果。

## 核心设计取舍(一句话版)

- **完全独立建表**(`feedback_` 前缀 5 张表),不复用 `test_case` 体系,业务隔离。
- **`exec_run` 表零改动**:feedback 下发直接写 `exec_run`,靠**专用项目 `project_id` 天然隔离**
  (业务项目的执行结果页按 project_id 查,看不到 feedback 记录)+ `batch_id` 聚合统计
  + `payload.feedback_case_id` 软关联追溯。qalab-runner **零改动**。
- **三触发源共用一个下发内核**:定时/手动回归/勾选执行,最终都是「一批 feedback_case → 快照成
  exec_run」。
- **md 是结构化用例**(固定模板 + 12 列表格),拆解走**纯结构化解析**,不用 AI 生成用例正文;
  **仅** `auto_feasible∈{yes,partial}` 的用例在导入后用现有 AI 引擎补可执行 `script`。
- **机器人对接**用独立 `X-Bot-Token`(仿 `RUNNER_TOKEN`,与用户 JWT 分离);反馈类文件推到
  **固定专用「反馈测试」项目**,机器人侧无需知道 project_id。
- **定时调度**用平台内置 **APScheduler**(全新引入,平台此前无任何调度机制)。

## 架构与数据流

```
机器人 --POST /api/feedback/ingest (X-Bot-Token, multipart: md/zip)-->
    [1] 校验 token → 定位固定专用「反馈测试」项目
    [2] 落 feedback_import(status=parsing)
    [3] zip 解压/单 md → services/feedback_parser 逐个解析(固定模板,容错)→ 落 feedback_case(status=draft)
    [4] 立即返回 {import_id, file_count, case_count}   ← 机器人拿到即走,不等 AI
    [5] 后台线程:对 auto_feasible∈{yes,partial} 用例逐条 AI 补 script(AI_MAX_CONCURRENCY 限流)
        → 每条补完置 status=ready;整批完成 import.status=done

前端「反馈测试」:
    /feedback-imports   导入记录(批次 + 手动上传兜底 + 解析/补script进度)
    /feedback-cases     反馈用例库(按需求/测试点分组;编辑/勾选)
                         ├─ 勾选「加入集」→ feedback_set_case
                         └─ 勾选「发送执行」→ 下发内核(ad-hoc, set_id=None, trigger=manual)
    /feedback-regression 回归用例集(建集/入集/设 cron/开关/看 next_run_at)
                         ├─「立即回归」→ 下发内核(set_id, trigger=manual)
                         └─ 定时到点 → APScheduler → 下发内核(set_id, trigger=auto)
    /feedback-results   回归结果(feedback_run 批次列表 → 钻取 batch 内 exec_run 逐条 pass/fail)

下发内核(三源共用):
    选定 feedback_case 列表 → 生成 batch_id → 每条快照成 exec_run
        (test_case_id=None, checklist_item_id=None, project_id=专用项目,
         payload={title,steps,expected,script,kind,feedback_case_id})
    → 建 feedback_run(batch_id, set_id?, trigger, started_by)
    → qalab-runner 轮询拉取执行 → PATCH 回写 verdict/report 到 exec_run
    → 结果页按 batch_id 聚合 exec_run 现算 total/passed/failed/blocked
```

## 机器人对接接口(`api/feedback.py`)

```
POST /api/feedback/ingest
  鉴权: 头 X-Bot-Token == settings.FEEDBACK_BOT_TOKEN(空则 503 拒绝一切,仿 RUNNER_TOKEN)
  Content-Type: multipart/form-data
  fields: file=<.md 或 .zip>(必填); note=<可选备注>; source_bot=<可选>
  流程: 见架构 [1]~[5];单文件上限 20MB(zip);解析失败的 md 记入 import.error 并跳过,不整批失败
  返回: ok({import_id, file_count, case_count, script_total})
```

**专用项目**:`main.py` startup `ensure_feedback_project()`,固定 slug(如 `__feedback__`)
幂等建项目(仿 seed admin),token 即绑定该项目。

## md 解析器(`services/feedback_parser.py`,纯函数)

按固定模板逐段抽取,**容错已见差异**(`##` vs `###` 反馈概述、一级标题带不带需求编号):

| md 段落 | → 字段 |
|---|---|
| 一级标题 `# 测试用例 · xxx · V1.0` | req_title |
| `## 需求信息` 的「需求链接」 | req_url |
| `## / ### 反馈概述` 全段 | feedback_summary |
| `### 测试点 P-101 xxx` | point_code + point_title |
| 12 列表格每行 | case_no/priority/title/precondition/steps/expected/category(类型列)/auto_feasible+auto_reason(拆「自动化(可行/优先级/理由)」列) |

- 表格「自动化」列格式 `yes / high / 理由` → 切分出 `auto_feasible=yes` + `auto_reason=理由`。
- 步骤内 `<br>` / `1. 2. 3.` → 规整为多行 steps。
- `exec_kind`:`auto_feasible=no` → `manual`;`yes/partial` → 初判 `gui`(被测 Electron GUI 为主)。
- 接口签名:`parse_md(text: str) -> {req_title, req_url, feedback_summary, cases: [ {...}, ... ]}`;
  `iter_zip(data: bytes) -> [(filename, text), ...]`。可脱机单测。

## AI 补 script(导入时自动全部补齐)

- ingest 后台线程遍历 `auto_feasible∈{yes,partial}` 的 case,复用 `ai.py::gen_script` 的同款
  逻辑(抽为 `services` 层可复用函数),按 case 的 steps/expected + 目标 page 生成结构化 `script`,
  写回 `feedback_case.script` + 推断 `page`,置 `status=ready`;失败写 `script_error`(不阻断其余)。
- 受 `AI_MAX_CONCURRENCY` 限流;`AI_ENABLED=false` 或引擎不可用时跳过补 script,case 保持 draft
  (仍可手动执行,payload 无 script 时 runner 侧兜底)。

## 下发内核(三源共用,`api/feedback.py` 内 `_dispatch_cases`)

```python
_dispatch_cases(db, project_id, case_ids, runner, trigger, set_id=None, started_by=None):
    去重保序 → 校验 case 存在/属专用项目/非 manual(整批校验)
    batch_id = 新批次号
    for case: exec_run(test_case_id=None, checklist_item_id=None, project_id, batch_id,
                       runner, kind=case.exec_kind, status=pending,
                       payload=json({title,steps,expected,script,kind,feedback_case_id:case.id}))
    feedback_run(project_id, set_id, batch_id, trigger, case_count, started_by)
    return {batch_id, run_ids, feedback_run_id}
```

三个触发源:
```
POST /api/feedback/regression/{set_id}/run   手动整集回归  → _dispatch(set 内 case, trigger=manual, set_id)
POST /api/feedback/cases/run  {case_ids:[]}   勾选即时执行  → _dispatch(case_ids, trigger=manual, set_id=None)
定时(调度器内部)                              → _dispatch(set 内 case, trigger=auto, set_id)  不额外开接口
```

其余接口:用例 CRUD(列表按 import/测试点分组、改 exec_kind、重补 script、删)、集 CRUD、
集设 cron/开关、结果查询(feedback_run 列表 + 按 batch 聚合 exec_run 明细)、导入记录列表。

## 内置调度器(`services/scheduler.py`,APScheduler)

- `requirements.txt` 加 `apscheduler`。
- `BackgroundScheduler` + `SQLAlchemyJobStore`(复用同一 DB,重启不丢 job)。
- `main.py` startup 启动调度器 + 从 DB 现有 `schedule_enabled=1` 的集重建 job;shutdown 关闭。
- job 可调用对象是**模块级函数** `run_regression_job(set_id)`(SQLAlchemyJobStore 要求可 import),
  自建 DB session → 查集内 case → 调 `_dispatch_cases(trigger=auto)` → 更新 `last_run_at`。
- 集设/改 cron 或开关 → `add_job/remove_job(id=f"fbset-{set_id}", CronTrigger.from_crontab(cron))`,
  回填 `next_run_at`。前端提供友好选择器(每天/每周 + 时间)转 cron 字符串存库。

## Global Constraints(遵循项目约定)

- 统一信封 `{code,msg,data}` + `ok()`;每 router 手写 `_to_out(db,obj)->dict`(枚举取 `.value`、日期 `isoformat`)。
- 不用原生 JSON 列(Text 存 JSON);两份 schema 手动同步(models + sql/schema.sql)。
- 全新表 `create_all` 自动建(不进 `_SKIP_TABLES`);**exec_run 零改动,无需 migrate**。
- RBAC:ingest 走 bot token;人工接口走 `get_current_user` + `assert_project_role`(专用项目 admin/member)。
- 无测试框架:验证用一次性 Python 脚本 + 真实参考 md/zip 打 ingest 端到端;解析器纯函数脱机验。
- runner 契约不变(payload/verdict/report 同 exec_queue)。
