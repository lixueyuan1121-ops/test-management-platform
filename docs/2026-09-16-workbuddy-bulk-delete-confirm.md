# WorkBuddy 执行权限确认卡适配

截图中的“检测到批量删除操作：累计删除数量 …，阈值 …”是 `SandboxInterceptCard` 渲染的 `InterceptCard`，与已有反问卡、计划确认卡不同。原测评等待循环没有处理该卡片，任务因此停在“待确认”。

同一组件也承载“检测到受保护文件修改”，提供“允许 / 本次会话内始终允许 / 拒绝”三个选项。该类型已补充接入，使用单次“允许”。

## 执行流程

1. 等待任务结果期间识别可见的拦截卡，按权限类型核对标题和选项。
2. 批量删除点击“允许本次删除”，受保护文件修改点击“允许”。按钮前的数字序号、选项顺序和默认高亮不影响单次授权选择；支持简体、繁体和英文文案。
3. 提交期间等待，卡片仍在时不按中间输出判断完成。已提交且仍高亮的同一项不重复点击。
4. 若客户端明确显示提交失败（按钮恢复可用、提交选中态清除），间隔重试；默认最多提交 3 次，仍失败则明确记录 `WORKBUDDY_CONFIRM_FAILED`。
5. 卡片消失后继续等待生成结束，当前轮完成栏稳定出现才采集答案、分享链接及 trace。连续出现新卡片时按新请求处理。

自动选择按已适配的权限类型匹配，选用单次授权。复用相同组件的其他权限卡保持待确认状态，整页正文或隐藏区域中的同名按钮不匹配。保留 WorkBuddy 原有反问、计划确认和分享逻辑；本次没有修改纳米 Work 驱动。

## 配置与验证

新增 WorkBuddy 专属配置：`interceptCardSelector`、`interceptOptionSelector`、`interceptMaxAttempts`、`generatingSelector`。选择器依赖组件语义前缀和 DOM 结构，不依赖构建哈希。

只读连接本机 WorkBuddy，确认页面为主文档，并检查安装包的 `InterceptCard` / `SandboxInterceptCard` 实现。真实 Chromium 回归按其 DOM 与提交状态复现截图场景；测试回调只更新页面计数器，没有执行任何删除命令。覆盖禁用、提交去重、失败重试上限、新卡片、同节点新请求、生成未结束、卡片读取期间卸载、隐藏卡片和其他权限类型。

155 项回归全部通过，包含 WorkBuddy 权限卡的三项选择、选项顺序变化、单次授权、失败重试及原有相关测试，以及纳米 Work 续作、算力豆、多轮分享、trace 和结果回填相关测试。

Mac WorkBuddy 5.5.6 的受保护文件修改卡已完成真机验证：核对当前任务的截图命令（生成并检查 `/tmp/g4.png`）后，用新逻辑点击一次“允许”。确认权限卡数量从 `1` 变为 `0`，发送按钮进入生成/停止态，原任务继续执行；没有将此验证表述为整个甘特图任务已经完成。

Windows 5.5.3 的批量删除原任务尚未现场重放。

发布生效步骤：将修复推送至 `main` 后，在服务器运行 `bash scripts/update.sh`；执行设备更新 Runner 并重新启动后加载新版逻辑。已有运行中任务不会因代码推送自动切换版本。
