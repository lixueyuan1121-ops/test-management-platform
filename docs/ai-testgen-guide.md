# AI 测试助手 · 生成与排障说明

> 面向 QA:用「AI 测试助手」从需求生成结构化测试点时,如何拿到更高的自动化执行率、以及遇到问题怎么办。
> api 类用例的配置/执行另见 [`api-testcase-user-guide.md`](./api-testcase-user-guide.md)。

## 用例类型与自动化

生成的每条用例有一个**执行类型 kind**,决定它能否被执行机自动跑:

| kind | 含义 | 能否自动执行 |
|---|---|---|
| **gui** | 客户端界面上单点操作+断言(2–4 步) | ✅ 走 step-executor |
| **e2e** | 跨界面的端到端流程(≥5 步) | ✅ 走 step-executor |
| **api** | 脱离客户端直接调接口 | ✅ 走 api-executor(**仅当接口能在客户端外鉴权**,见 api 指南「适用边界」) |
| cli | 命令行 | ✅ 走 claude |
| **manual** | 人工执行 | ❌ 不下发,占人力 |

**目标:manual 越少越好。** 生成侧已内置**「自动化优先」**倾向:

- 只要验证点能"在界面上操作并做**客观断言**",一律优先判 **gui/e2e**,不轻易判 manual;
- 后端/接口行为若在界面有可观察结果(创建后列表出现、删除后消失、报错弹提示),**优先设计成 gui/e2e**(界面触发+断言),而非 api;
- 只有**依赖人主观判断**的(美观、流畅、体验)才判 manual;
- 项目**没配 api 契约**时,本会判 api 的验证点会**自动改判 gui/e2e**(因为这类系统接口多半客户端外调不通)。

> 前提:gui/e2e 能落地,靠项目里有对应的**选择器 key**(在「选择器管理」用探测积累)。key 越全,能自动化的用例越多。

## 「补选择器可自动化」标识 —— 把降级用例捞回来

有些用例本该是 gui/e2e,但**因为用到的选择器 key 还没注册**,生成时被降级成了 manual。平台会给这类用例打一个醒目标识,让你知道"**差一点点就能自动化**",并**直接列出缺哪些 key**(无需 hover):

- **AI 测试助手 · 生成结果表**:测试点下方直接显示橙标签「补选择器可自动化 · 补: navTasks, submitBtn」——生成完当场就看到;
- **用例库 · 执行类型列**:同样的标签,并在标签内换行列出缺的 key;
- **用例库 · 顶部筛选**:勾选「**仅待补选择器**」可一键筛出全部这类用例,勾选后旁边显示条数(如"仅待补选择器 · 12"),便于批量处理;
- **用例详情**:「判定理由」一行显示完整文案。

该标识**可信**:只有"补齐这些 key 后确实能通过校验"时才承诺"补齐即可执行";若还有其它问题(如缺断言),会注明"补齐后仍需修其它问题"。

**闭环操作(把 manual 转成自动化):**

1. 用例库里找带「补选择器可自动化」标签的用例 → 悬停看缺的 key;
2. 去「选择器管理」,用**设备探测**把这些 key 补进注册表;
3. 回到该用例点**「重新生成 script」**(或重新生成整批)→ 标签消失,用例变为可执行 gui/e2e。

如此逐批把"降级人工"的用例转成自动化,持续减轻人力。

## 生成的稳健性(平台已做的保护)

- **解析容错**:模型输出被网关截断、前后夹了多余文字、或个别用例格式坏时,平台会**逐条抠出能用的用例**(而不是整批丢弃)。所以"生成成功却一条没出"的情况已大幅减少。
- **script 非法自动降级**:gui/e2e 若凑不出合法断言/注册 key,自动降级 manual(并可能带上「补选择器」标识),**不会把坏脚本派到执行机**。
- **重生 script 超时放宽到 60s**:单条「保存并重生 script」调 AI 较慢,前端已单独放宽超时,不会因为默认 15s 提前报错。

## 常见现象

| 现象 | 说明 / 处理 |
|---|---|
| 生成完提示「未检测到有效测试点」 | 模型没产出可解析的用例数组。看该次任务的 `output_raw`(错误信息带尾部片段);多为需求太空泛或模型跑偏,**换更具体的需求重试**。 |
| 大量用例是 manual | 该项目选择器 key 太少,或需求偏主观。先在「选择器管理」补 key,再看带「补选择器可自动化」标签的用例批量转化。 |
| 想要更多 gui/e2e、更少 api/manual | 已是默认倾向。若仍偏多 manual,通常是"没有可断言的界面元素/key"——补 key 是根本解。 |
| api 用例全 fail(110001/4001) | 被测系统客户端内签名,api 客户端外调不通 → 改判 gui/e2e(见 api 指南「适用边界」)。 |
