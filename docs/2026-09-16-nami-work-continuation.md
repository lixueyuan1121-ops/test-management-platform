# 纳米 Work「继续工作」测评适配

## 问题与调整后的流程

纳米 Work 可能先给出文字答复，再显示 `work-continuation-card`（“需要更深入的结果？继续使用「工作」”）。点击“继续工作”会在同一会话追加用户提问和后续回答。原执行器以首轮消费栏作为完成信号，桌面巡检还忽略了交互处理的返回值，可能在后续工作开始前就收尾。

现在一条测评的流程为：

1. 发送测评题目，记录当前会话原有轮次。
2. 继续处理已有的反问、工具确认和弹窗；检测最新回答内的“继续工作”卡片，按钮可用后点击一次。
3. 记录追加轮次的边界，等待新回答完成。启动期间不重复点击，首轮消费栏不再代表整条测评完成。续作期间沿用整条任务的超时预算。
4. 取得最终回答与产物后，打开分享面板，校验“全部”前确实是对勾，且每一个列表项都已选中。部分选中的横线不算全选；不能确认时不生成不完整分享。
5. 将该测评初始回答和自动追加各轮的算力豆合计回填。上一条测评的历史消耗不计入；任一轮数值尚未出现则等待、按原机制刷新核对和补填，不以部分和或零代替。
6. 回填一次测评结果。显式配置的下一条多轮用例重新建立消费边界。

例如：同一条测评首轮 `1 算力豆`、点击继续工作后 `23 算力豆`，最终回填 `24`。分享包含这两轮完整对话，正文回填后续工作的最终回答。

## 失败与任务隔离

- 点击后没有新回答、卡片显示失败、空闲状态下按钮持续不可用，均显式报错，不将首轮文字误报为完成。
- `execution.workContinuationMaxRounds` 默认 `3`，防止循环续作；达到上限且仍有卡片时报告未完成。
- `execution.workContinuationStartTimeoutMs` 默认 `120000`，约束续作启动或空闲卡片就绪等待。正常生成中按钮禁用不消耗空闲等待预算，仍受整条任务 `responseTimeout` 约束。
- 桌面并发的每条任务独立保存原始基线、续作轮次和等待状态；切换对话后恢复对应任务的状态。
- 纳米 trace 在续作前收齐缓冲，只切换答案/思考的轮次边界，保留各轮工具调用。首轮更长的说明或迟到的旧 final 不会覆盖后续较短的最终答案。普通新测评仍按原流程重置采集器。
- WorkBuddy 的选择模型、新建任务、交互、分享与 DOM trace 实现未修改。`ws-trace.js` 中 WorkBuddy 使用的文本清洗及 MCP 辅助函数未修改。

## 验证

浏览器回归使用真实 Chromium，并按公开客户端组件复现开放 Shadow DOM 卡片与分享面板，覆盖：

- 点击去重、延迟启动、旧 footer 保留、后续 footer 未出现。
- footer 先到、卡片随后渲染；失败、禁用、启动超时、续作次数上限。
- 生成中禁用卡片和工具确认的处理顺序。
- 两条桌面任务交替巡检，续作状态与算力豆互不串用。
- 多轮完整消费、历史用例排除、小数精确累加、缺失消费不返回部分和。
- 全选横线/对勾、逐项校验、已全选不反向取消、旧剪贴板拒用。
- 纳米 gateway 原生桥接 trace 的跨轮工具保留、短答案与迟到旧 final。
- 原有纳米 trace、多轮用例，以及 WorkBuddy 相关回归。

真实纳米 Work 客户端另外执行了一条自拟无私有数据的文本文件小样本：任务完成，回填 `2 算力豆`，生成[验证分享](https://work.n.cn/share/4426mrmz7nie36d7?showReturn=0)，trace 为 `nami_gateway`、`captured`，丢帧与轮询错误均为 `0`。该小样本直接完成，未触发续作卡片；卡片分支与多轮全选由上述组件复现场景验证，不能将其表述为真实线上续作端到端验证。

发布生效步骤：将修复推送至 `main` 后，在服务器运行 `bash scripts/update.sh`；执行设备更新 Runner 并重新启动后加载新版逻辑。已有运行中任务不会因代码推送自动切换版本。
