# Claude Messages 调用方式

用于需求分析、场景、用例及单条 script 生成。保留原提示词、来源校验、验收覆盖检查及脚本校验，不启动 Claude CLI、插件或工具轮次。

默认仍为 `AI_CLAUDE_TRANSPORT=cli`。需要启用时在部署环境配置：

- `AI_CLAUDE_TRANSPORT=messages`
- `CLAUDE_MESSAGES_BASE_URL`：当前模型服务或代理地址，支持根地址和 `/v1` 后缀。
- `CLAUDE_MESSAGES_API_KEY`：通过环境变量注入，不提交凭据。
- `CLAUDE_MESSAGES_MODEL`：明确指定当前使用的模型，不自动换模型或供应商。
- `CLAUDE_MESSAGES_MAX_TOKENS=16384`
- `CLAUDE_MESSAGES_IDLE_SECONDS=90`；总时限继续使用 `AI_TIMEOUT_SECONDS`。

平台不会读取用户的 Claude 配置文件或自动复制凭据。8001 的本地验证启动器单独从已有本机 Claude 配置注入当前代理、认证及 Opus 模型；该启动器不属于提交代码，线上默认行为不变。

## 完整性与恢复

- 前端等待期间持续有心跳；HTTP 请求由独立协程管理，取消和超时会关闭连接并释放并发槽。
- 只有收到正常 `message_stop` 且存在正文才返回结果。长度截断、错误事件、缺少完成标记不视为成功。
- 在总时限内，只对没有任何正文的超时、连接中断和临时服务错误重试一次。已有正文的请求不自动重跑。
- 同一响应重复出现 `message_start` 会明确报错并保留部分正文，禁止拼接不同次响应。这是实测上游的一种异常，不是用户重复提交。
- 日志记录任务、批次、调用编号、HTTP 状态、请求编号（上游提供时）、模型、首字时间、返回长度和重试次数，不记录凭据、需求正文或思考内容。

已确认：同一份完整需求经原 CLI 多次无正文超时，经 Messages 两次完整需求理解约 102 秒、109 秒完成，场景约 23～25 秒完成。第三方模型仍可能发生断流或响应重启；这一实现处理并暴露失败，不能保证上游永不故障。
