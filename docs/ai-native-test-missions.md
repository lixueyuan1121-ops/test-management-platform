# AI Native 测试目标：使用与流程调整

2026-09-13。本次将已有功能测试能力接成持久化目标闭环：输入测试目标与需求，AI 持续准备和跟进，人确认业务意图与执行授权，最后按证据给出质量结论。

第二轮已增加具体场景确认、独立用例审查与证据内容核验，详见 [流程调整与上线说明](ai-native-quality-loop.md)。

## 现在怎么使用

1. 从工作台的「进入测试目标」，或「测试指挥官 → 测试目标」进入。
2. 新建目标，说明希望验证的结果，选择项目与关联任务。可导入新需求，也可选择已有需求分析。已有 AI 测试助手确认验收后，新增「以此验收版本开始测试目标」入口。
3. 新需求支持粘贴正文、读取文档链接、上传 Word / PDF / 文本 / 图片，并补充图片。复用既有图文提取和识别能力；无法识别、内容截断、图文冲突仍会明确保留。
4. AI 分析完成后，先看产品理解、未处理问题、推导规则和图片不确定项。对照原文和图片确认本期范围及验收条件。历史人工确认会作为参考，并展示相同规则的变更字段；不会自动代替本期确认。
5. 确认验收版本后，后台自动查找可复用用例、为覆盖缺口补充用例、制定方案。方案显示选择理由、验收关联来源、复用情况、未覆盖条件和风险。
6. AI 独立审查方案中的用例及脚本；处理审查问题后，核对所选用例的前置、步骤、预期及验收关联，选择自己登记的执行设备、执行时间预算和是否允许环境复测，然后「确认方案并开始执行」。这次明确操作同时记录所选用例的人工采纳与覆盖核对。
7. 后台等待执行机回传，对失败 / 阻塞自动调用 AI 归因，并按授权条件有限复测。无需在多个页面手动接续，也不依赖浏览器保持打开。
8. 后台逐项核验实际断言与可读取截图，之后查看验收证据、质量结论、原始失败和重试链。需要修订用例、检查完整执行报告、人工纠偏或登记缺陷时，进入原有用例库与执行结果页面。下一轮使用新目标保留本轮证据。

## 原有流程具体怎样调整

| 环节 | 原来 | 现在 |
| --- | --- | --- |
| 工作入口 | 分别进入 AI 助手、用例库、执行结果 | 工作台 / 指挥官以「测试目标」为主入口；原有页面仍可独立使用 |
| 需求处理 | 每次逐段查看文档，独立触发分析 | 新目标保存后自动分析正文与图片，先突出需要决定的内容 |
| 历史经验 | 依赖人员记忆与手工查用例 | 同项目已确认规则提供上下文；展示变更与确认来源；严格匹配业务条件才复用历史用例 |
| 验收确认 | 确认后还要手动启动生成 | 确认不可变验收版本后，后台自动准备用例和方案 |
| 用例准备 | 通常重新生成整批，再手工挑选 | 优先匹配既有覆盖，只对缺失验收条件调用生成；AI 在受限候选中规划 |
| 执行下发 | 去用例库挑选设备、逐次下发 | 在目标内核对具体方案，一次授权设备、用例和预算；后续流程自动衔接 |
| 失败处理 | 手动点归因、判断是否重跑 | 自动归因；只有满足授权和严格条件的环境阻塞可复测一次；其他失败进入风险结论 |
| 质量判断 | 看生成数、采纳数或批次通过率 | 按全部已确认验收条件逐项核对版本、人工核对、执行与证据；明确区分流程完成和发布评审条件 |
| 版本变更 | 容易继续使用旧方案 / 旧通过记录 | 需求修改使旧方案失效；用例修改阻止旧方案下发并使旧证据过期；已执行目标通过新一轮继续 |
| 页面刷新 / 服务重启 | 用户需要重新寻找结果并手工接续 | 目标、阶段、方案、任务指针和推进记录落库；恢复后继续等待，失败节点可显式重试 |
| AI 战绩墙 | 生成、采纳、成本与估算节省时间为主 | 首屏新增目标收口、具备评审条件、有效验收证据、人工介入和目标耗时；生成统计作为另一组信息 |
| 项目问答 | 指挥官的主要形式 | 移到「项目问答」标签，保留现有问答和操作草稿能力 |

正常主线有两类关键人工决定：确认产品验收，核对并授权执行方案。缺失资料、AI 失败、版本变化或权限变化会产生额外处理点，不用减少确认次数来换取不可靠的结论。

## 证据与结论口径

- 分母是当前目标验收版本中**全部已确认验收条件**。未选择执行、人工用例、方案预算未纳入和生成遗漏，都保留为覆盖缺口。
- 一个条件只有在相关用例仍与授权内容一致、用例保持采纳、目标内有明确人工覆盖核对、执行通过，且独立核验的实际断言或截图支持该条件时，才计为证据齐备。只有报告或链接不能计入；图片和业务语义的 AI 判断仍需人工校准。
- 同一条件关联多个场景时，任何失败、阻塞、待执行、缺证据或计划内未执行场景，都不能被另一条通过记录掩盖。
- 重试后通过保留为「重试后通过 / 不稳定」，不直接计为稳定验收通过。原失败、同一执行快照、重试父记录和归因建议均保留。
- 仍有待确认规则或验收版本已变化时，不给出“具备发布评审条件”。本期明确排除的规则及原因保留在报告数据中。
- 流程收口保存报告快照。当前证据另行重算，因此事后改判、用例修订和需求变更不会改写当时的历史结论，也不会继续把旧结论显示为当前有效结果。
- 发布决定仍由人作出；平台输出可评审的证据和风险。

## 自主推进的范围与限制

- 本次闭环覆盖功能测试。目标完成不会自动把关联任务改为上线 / 关闭，也不自动回写旧验收清单状态。对话测评、性能测试、流水线发布仍使用既有流程，尚未统一纳入目标调度。
- 目标后台协调器每约 3 秒扫描；AI 操作使用已有持久化队列。刷新 / 关闭页面不取消后台任务。服务需保持运行；中断的 AI 任务有错误和重试入口，不承诺模型调用永不失败。
- 每次方案上限可设 1–50 条；执行预算可设 5–240 分钟，包含排队时间。这是执行阶段的调度预算，不是全部模型调用的金额预算。
- 自动复测默认关闭。开启后，必须是执行机判为阻塞、AI 归因为 environment、置信度至少 0.85，且该用例还未复测过，才复制原快照到同一设备重试。功能失败不会因 AI 归因而被自动重跑或改判。
- 「暂停后续推进」暂停协调器的新动作；已经下发到执行机的任务可能继续。预算仍会收口，未启动项停止下发；已运行的远端进程不会被强制杀死。服务停机、轮询间隔和远端运行会影响收口时刻，因此不是硬实时终止保证。
- 权限或验收版本变化会阻止后续推进，并停止尚未开始的执行。用例执行内容变化会使本轮收口并保留原快照，下一轮重新规划。
- 复用仅限同项目、当前有效的历史验收版本，以及人工采纳且内容未改变的用例；范围、业务条件、预期及验收文本必须严格匹配。候选检索有数量上限，不能保证找到历史库中的全部可复用项。模型相似度不自动传递人工确认。
- 不自动修改业务预期、无限重试、对外发送通知、上报外部缺陷或发布产品。归因失败会显示错误并保留原执行结果，流程仍能生成缺口报告。
- 原有尚未关联验收版本的历史用例和旧生成任务保持兼容，不自动批量转换为已确认知识。

## 成效统计

目标指标按创建时间窗口统计，并遵循项目查看权限：目标创建 / 收口数、当前具备发布评审条件数、已收口目标的有效验收条件数、平均人工介入次数、从创建到收口的平均分钟数（包含人工等待）。缺少样本显示「—」。

实际费用只展示已采集到的用例生成费用，并同时给出样本数和不完整说明。需求分析、方案规划及执行的费用没有完整采集，不估算总成本。AI 误判率和确认缺陷数仍需建立独立人工复核标注后再统计，不以归因建议冒充确认缺陷。

## 技术与上线说明

新增 `test_mission`、`test_mission_event`、`test_mission_run` 三张表，随现有启动建表流程创建。文档字段采用兼容 MySQL 5.6 的 LONGTEXT，不新增原生 JSON 列，不修改旧用例验收关联的唯一约束。任务推进与 AI / 执行队列指针在同一事务提交；行锁、版本校验和执行内容指纹用于防止重复下发及使用过期方案。

新增 API 位于 `/api/test-missions`；现有分析、用例、执行和项目问答 API 保持兼容。前端产物需与后端一起更新并重启服务，不能只替换静态页面。

22 项目标 / 需求集成测试、既有 AI 队列 / 调度 / 项目问答检查以及浏览器回归通过，前端构建通过。本次验证使用隔离数据库、模拟模型和模拟执行结果，不调用真实用户环境的执行机。已验证持久化恢复、审批版本冲突、未知候选拒绝、跨项目与只读权限、历史复用、证据缺口、有限重试及原始失败保留；页面验证覆盖授权、刷新恢复、报告展示和窄屏布局。已有需求图片与验收确认流程继续回归。
