# 批量判定并发加速

## 流程变化

| 入口 | 原流程 | 调整后 |
| --- | --- | --- |
| 手动批量判定、单条判定 | 与其他 AI job 共用默认 2 个工作线程 | 进入判定专用队列，默认 4 个工作线程 |
| 一条龙自动判定 | 在编排线程中逐条调用模型 | 逐条入同一判定队列，等待整批任务终态后生成综合评价 |
| 多个任务同时判定 | 自动任务各自串行，手动任务另走队列 | 自动、手动及不同批次共用判定并发上限，不为每个批次再创建线程池 |

判定仍使用原来的模型、提示词、证据校验和多数票规则。每条 run 独立读取资料、判定和落库；完成一条就保存一条，前端原有 job 轮询和结果进度继续可用。

现有「批量判定」按钮的选择范围仍包含已判定条目，再次主动点击会对已完成条目创建新判定版本。对单条异常执行「重判」会更新任务对应批次的同一条结果，刷新任务详情即可看到；已生成的综合评价需另行重新生成。

## 并发与失败处理

- 判定工作线程不再占用通用 AI job 工作线程；需求分析、用例生成等仍使用原线程数。模型调用仍共享底层引擎并发限制，所以不能保证其他 AI 调用完全没有资源竞争。
- 同一执行项重复点击、自动与手动同时提交时，复用其排队中或运行中的判定 job，沿用该 job 的模型和票数；已完成后主动重判才创建新 job。
- 队首抢占失败会立即尝试下一条，避免空闲线程固定等待 2 秒后才重试。
- 错误信息包含 `API Error` 时（忽略大小写，也兼容 `APIError`）默认等待 5–6 秒后重试当前票一次，包含 HTTP 200 空响应/畸形响应，以及已返回部分正文后报 API Error 的情况。错误 result 的报错文案不作为判定正文。成功票和其他已完成条目不重跑。
- 其他错误沿用原策略：无输出的限流或临时服务错误可有限重试；普通超时、鉴权/参数错误、部分输出后的非 API Error、判定正文格式错误不自动重跑，DeepSeek 已耗尽内置退避重试也不叠加重试。`EVAL_JUDGE_TRANSIENT_RETRIES=0` 可关闭上述额外重试，最多可配置额外 2 次。
- 重试失败原因保存在该次判定的票据记录中，不改变实际票数。
- 单条判定失败不阻断其他条目，也不计作成功判定。整批 job 都结束后才进入综合评价；若编排等待中断、超时或任务记录丢失，保留已有结果并停止本次综合评价。
- 任务换批时，旧批编排停止等待，尚未开始的旧自动判定会跳过；人工选择历史批次重新判定仍可执行。
- 每条 job 使用独立数据库 session，编排等待通过短 session 轮询，等待间隔不占连接。

## 配置与生效

```dotenv
EVAL_JUDGE_CONCURRENCY=4
EVAL_JUDGE_TRANSIENT_RETRIES=1
AI_WORKER_CONCURRENCY=2
AI_MAX_CONCURRENCY=6
DEEPSEEK_MAX_CONCURRENCY=2
```

前两项为新增配置，有默认值，已有 `.env` 不必填写也会生效。后三项沿用原配置。模型上限小于判定线程数时，多余调用仍会等模型槽位；上游服务的请求数及 token 配额仍然生效。

这些上限均为**每个后端进程**，多实例部署时总并发会叠加，应结合上游额度分配。更新代码并重启后端后生效，无需数据库迁移、前端构建或更新执行设备 Runner。可将判定并发设为 `1` 或 `2` 后重启以降低负载。

## 验证

- 18 个相关回归模块通过，包含队列、写库失败恢复、模型槽位、判定证据、任务编排、综合评价、报告及 DeepSeek 退避逻辑。
- API Error 重试调整后，判定并发、证据校验、中断恢复和结果一致性共 60 项测试通过。
- 新增 23 项测试使用真实工作线程、独立文件数据库和可控模型事件，覆盖共享并发上限、普通任务可继续执行、重复提交去重、部分失败、逐条落库、综合评价等待、换批及历史重判、等待超时、投票重试和重复启动保护，以及 API Error 的 CLI 错误 result/助手错误消息、部分输出后报错、大小写、次数限制与正常正文误匹配。
- 同一组 12 条判定、每次模拟模型响应等待 150ms：1 并发 `2.103s`，4 并发 `0.548s`，约 `3.8×`。该测试验证调度加速，不代表线上模型压测结果。
- 回归将模型替换为可控测试对象，没有使用真实测评资料做线上模型压测。

纳米 Work、WorkBuddy 的客户端任务执行、交互卡片、分享链接与 trace 抓取代码均未修改。

## 综合评价 API Error 重试

手动「生成综合评价」和一条龙自动综合评价共用重试逻辑。模型错误事件、错误 result 或调用异常中包含 `API Error` 时（忽略大小写，也兼容 `APIError`），默认等待 5–6 秒后重新生成本次报告一次。已返回部分正文后报错也会重试；失败尝试的正文丢弃，不与新报告拼接，错误 result 不作为报告保存。

- 重试期间保持生成中状态，先释放失败调用的模型槽位和子进程，再退避。成功后保存报告及分享码，手动任务只通知一次；重试仍失败则正常落失败状态，并保留错误原因。
- 只重试综合评价的模型调用，不重跑已判定结果。正常报告中提及 API Error 不触发重试；普通超时、无有效 HTML、消毒或写库失败不触发这项模型重试。
- 重试沿用同一份输入和生成令牌。退避期间如发生重新生成或批次结果变化，旧请求停止；历史批次生成不会覆盖当前批次报告。
- 自动流程原有的并发繁忙退避仍保留；一旦本次生成遇到 API Error，外层不会再叠加繁忙重试次数。
- 新配置 `EVAL_SUMMARY_API_RETRIES=1` 表示额外重试一次；`0` 关闭，最多额外 `2` 次，第二次等待 10–11 秒。每次模型调用仍受原有超时约束，失败后重试会增加总耗时。

更新代码并重启后端后生效，已有 `.env` 不必补填；无需数据库迁移、前端构建或更新 Runner。

新增 21 项离线回归覆盖两种入口、HTTP 200 畸形响应、错误 result、流异常、部分输出、大小写、重试上限、流资源释放、任务状态、分享码、通知次数和批次隔离。模型及通知使用测试替身，没有调用真实模型或发送真实通知。

## 综合评价状态展示

任务列表、详情页的「综合评价」页签和评价正文区域均显示当前状态：未生成、排队中、生成中、自动重试中、已生成、生成失败。评价区域同时显示已等待时间、模型已返回的字符数、自动重试次数及失败原因。失败后可直接重新生成；网络暂时断开会提示状态连接异常，并继续查询，不把网络错误误判为模型生成失败。

状态按执行批次保存在后端，刷新页面或关闭后重新打开仍可恢复。详情每 3 秒读取轻量状态接口，任务列表对活跃任务每 8 秒更新，不反复加载整批执行明细及 trace。模型输出进度最多每 2 秒写入一次，完成后才获取完整报告，不展示虚假的完成百分比。

手动提交时即保存排队状态，重复提交复用未完成的生成任务；选择历史批次时生成、轮询均使用所选批次。失败、取消、服务重启或生成跳过都有可恢复的终态及原因。旧生成任务不会覆盖重试后或重新生成的报告。

本次状态展示变更需要同时更新前后端。后端启动会幂等补充 `eval_batch_summary.summary_progress` 列，保留已有报告，无需手动改库或更新执行设备 Runner。

状态新增 9 项后端测试，覆盖真实入队/消费、进度持久化、重复提交、启动前失败、重启恢复、历史批次、旧任务失效及存量数据库迁移；另有浏览器回归覆盖状态流转、刷新恢复、批次切换、网络恢复和页面关闭后的轮询清理。
